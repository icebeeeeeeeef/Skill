# Codebase Onboarding（上手陌生代码仓库的方法论）

## 核心理念

学习的主体必须是用户本人，Agent 只是加速器。
用户“读完没记住”的根因是大脑处于被动接收状态。记忆与理解只在主动加工时产生：带着问题检索、自己复述重构、预测后被打脸。

因此本 skill 的最高原则：

> 检索、解释、概述交给 Agent；
> 推演、决策、记忆必须用户自己来。

> 凡是用户将来要从脑子里调出来的东西，比如 oncall、排查 bug、主导方案，
> 就必须先经过用户大脑加工一遍，绝不能让 Agent 代加工。

## Agent 的角色边界

Agent 应该做：
- 扫描 README、配置、文档，产出服务定位概述
- 列目录结构含义，定位入口，列出外部依赖
- 解释陌生语法、缩写、局部代码
- 检索调用关系，比如“这个函数被哪里调用”
- 充当考官：挑战用户的理解，找出遗漏的 corner case

Agent 不应该做：
- 直接给出“完整梳理好的主链路”让用户被动读
- 替用户做方案决策与取舍
- 替用户走完主链路 trace 和画图
- 让用户误以为“听一遍就懂了”

当用户请求“帮我梳理整个项目/主链路”时，不要直接输出完整链路，而应：
1. 先提供粗地图：模块划分、入口、依赖，用于定位。
2. 引导用户自己 trace 主链路。
3. 让用户复述，再由 Agent 挑刺补漏。

## 通用方法：四层下钻法

从外往里读，每层只回答固定问题，答完再下钻。绝不一开始就钻细节。

### 第 0 层：服务定位（不碰代码）

- 解决什么问题？上游/下游是谁？
- 输入是什么，输出是什么？
- 怎么被触发？定时、接口、消息、手动命令？

Agent 扫文档给概述，然后让用户用一句话复述；复述不出即没懂。

### 第 1 层：骨架

- 目录结构代表的模块划分
- 入口在哪：main、启动类、CLI entry
- 核心配置：连了哪些 DB、中间件、外部 API
- 核心数据模型或领域对象

Agent 负责列目录、找入口、列依赖；用户负责建立心智地图。

### 第 2 层：主链路

- 选一条最核心的业务流程，从入口亲手 trace 到底
- 边走边画时序图或调用链，图必须用户自己画
- 卡住时才让 Agent 解释局部

这是 oncall 能力的来源，不可代劳。

### 第 3 层：细节与边界

按需再看：
- 异常处理
- 重试
- 边界条件
- 并发
- 事务

用到哪块查哪块，不一次读完。

## 母题问题清单

每次读代码的唯一目标：消灭清单上的一个问号。答完即停，绝不顺手乱翻。

### 通用后端服务母题

1. 输入输出与触发方式
2. 核心数据模型
3. 主链路：请求或任务从进入到完成经历了什么
4. 依赖了哪些外部系统，挂了会怎样
5. 一致性与事务边界
6. 错误处理与重试
7. 可观测性：日志、指标、健康状况
8. 性能与资源约束：并发、限流

### 数据迁移服务专用母题

1. Source / Sink：从哪迁到哪？连接与配置在哪管理？
2. Extract 抽取：一次拉多少？分批/分页策略？按什么字段切分？
3. Transform 转换：字段映射规则在哪？清洗、格式转换、默认值？
4. Load 写入：批量还是单条？写失败怎么办？
5. 一致性：
   - 幂等性：迁两次会不会重复？去重靠什么？
   - 断点续传 / Checkpoint：挂了重启从哪开始？进度存哪？
   - 数据校验：迁完怎么验证源与目标一致？
6. 容错：重试？错误数据或死信怎么记？部分失败是中断还是跳过？
7. 可观测性：关键指标、速率、失败数、进度
8. 性能与资源：并发度、限流、是否会打爆源库或目标库

对数据迁移服务，幂等、断点续传、一致性校验这三块必须用户亲自推演失败场景，因为这是将来半夜 oncall 真要查的东西。

## 环节与角色分配

| 环节 | Agent 做 | 用户做 |
|---|---|---|
| 服务定位 | 扫文档给概述 | 一句话复述 |
| 骨架 | 列目录、入口、依赖 | 建立心智地图 |
| 主链路 | 卡住时解释局部 | 亲手 trace + 画时序图 |
| 核心转换或业务逻辑 | 解释陌生语法、算法 | 逐行精读、找 corner case |
| 一致性、幂等、容错 | 确认是否有该机制 | 推演失败场景 |
| 边界、异常 | 列出可能异常路径 | 判断真实风险 |
| 验证理解 | 当考官挑战用户 | 把理解讲出来 |

## 推荐执行节奏

1. 第 0~1 层：Agent 辅助，产出用户自己画的模块地图和一句话服务定位。
2. 主链路：选核心流程，亲手 trace，画端到端时序图。
3. 对照母题清单：逐条去代码确认，答不上的标红。
4. 跑起来：本地启动，造小批数据，打断点单步走，看数据真实流动；故意制造一次失败，验证容错或断点续传。
5. 收尾验证：把时序图和清单答案讲给 Agent 听，让它挑刺补漏。
6. 做一件小事：改一个小 bug 或加一个小功能。

## 心法

把 Agent 当成“很懂这个项目、但不能完全信任、且不会替你背锅的同事”：

- 让他指路、review 思路
- 不把要署你名字的方案直接交给他写
- 不因为他讲了一遍就认为自己懂了

始终让自己的大脑处于“输出 / 推演”状态，而不是“接收”状态。

# 清晰叙事表达

## 目标

把读者从“知道问题但不明白答案”带到“能用自己的话复述结论和原因”。主线、例子、标题和格式都是降低理解成本的工具，不是必须完成的写作仪式。

优先级从高到低是：事实正确、结论清楚、语言容易读、结构便于定位、文风自然。不要为了像一篇完整文章而增加术语、段落、过渡或篇幅。

## 何时使用

适合概念讲解、技术设计评审、方案对比、架构解释和调研结论。它解决的是“信息都有，但读者难以理解为什么”的问题。

不适合 API 参数速查、命令或配置步骤、纯数据报表、简短状态更新。此类内容应优先选择最容易查找的列表、表格或代码块，不要强行写成叙事。

## 写作前的判断

先在内部确定一句话结论：读者读完后应能判断什么。再选择最省力的表达形式：

- 问题本身有因果链时，用简短叙事：问题 → 原因 → 方案或结论 → 适用边界。
- 读者需要在多个选项间做选择时，直接按目标、差异、取舍和结论比较；必要时用表格。
- 读者需要执行操作时，使用按顺序的步骤，不为“主线”改写成散文。

没有能推动结论的因果链，就不要虚构 3–5 步叙事弧、路线图或章节问题。短回答先给结论；长回答只在结构确实复杂时给一两句地图。

## 核心规则

### 1. 用读者已知的语言建立起点

先说问题、现象或结论，再引入实现和细节。只有理解某个设计为什么存在必须回到动机时，才先解释动机；不要为每个小特性重复铺垫。

每段只推进一个问题。每句尽量只承载一个主要判断；一句里同时出现多层因果、多个限定或一串名词时，拆成两三句。能删掉而不损失结论或精度的话，删掉。

### 2. 术语应当是精度工具，而不是表达风格

优先使用用户已经使用的词、代码库已有名称和普通中文。不要为常见关系、步骤或现象自造名称、缩写、指标名或“框架”。

模型引入一个新术语前，先问：不用它是否仍能准确说清？可以就不用。确实需要时，先用普通语言说它做什么，再在同一句给出术语；例如“首个 token 返回前的等待时间（TTFT）”。除非用户要求术语表或该段在定义一组不可分的概念，同一段最多引入一个模型新造或外部术语。

来自用户、对话上下文或代码库的术语可以直接使用，不要反复解释用户已掌握的词；但也不要把这些词密集堆在一句里。出现连续两个以上专业名词时，先改写其中能用普通语言表达的部分。

### 3. 逻辑要清楚，但不要表演过渡

因果、对比和限制确实会影响判断时，用“因为”“所以”“但”“这意味着”等普通连接词直接说出关系。关系显然时，直接写下一句即可。

不要强制每节结尾抛问题，不要使用“接下来我们回到起点”“这引出一个更深的问题”一类只制造戏剧感的句子。删掉过渡后仍顺畅，就删掉它。

### 4. 例子只在它能消除歧义时出现

机制、边界或反例仅靠定义难以想象时，给一个最小例子。例子只保留理解所需的对象、动作和结果；数字、角色名和完整流程不是必需品。一个直白定义足够时，不补例子。

### 5. 让格式服务内容，而非服从配额

可以用 bullet 表示两到七项的步骤、条件、优缺点或并列事实；各项之间有顺序或因果也可以用列表，只要列表比长段落更容易扫读。用完整短句或能独立理解的短语，并在列表前说明它们的关系。

表格用于维度稳定的对照，图用于文字难以清楚呈现的结构或时序。不要为了显得完整而添加表格或图；图中的概念应在图前或图旁得到解释。

分析性长文的标题应表达该节要证明的判断；速查型内容可以使用描述性标题。使用真正的 Markdown 标题，不用加粗段落冒充标题。反引号只用于代码、命令、文件名和标识符。

### 6. 以结论收束，而不追求固定结尾

需要决策的回答，在结尾重申结论、适用条件和关键不确定性。单纯解释概念时，确认它已经回答开头的问题即可。不要机械加入“总结”“回扣主线”或自测题。

## 两个常用骨架

**概念讲解**：先用读者已知的现象说清问题；只有原有理解不足时，再引入新概念；说明它如何改变问题；最后说明边界。若定义已足够，停在定义，不要补完整故事。

**技术评审或对比**：先给建议或暂不建议的结论；解释目标和不可变约束；比较真正改变决策的差异；说明何时结论会反转。不要为了对称而罗列所有维度。

## 输出前自检

1. 开头是否让读者知道结论或要回答的问题？
2. 删去所有模型新引入的术语后，哪些地方真的失去精度？只保留这些术语，并在首次出现处说清含义。
3. 是否有一句塞进了多层因果、多个新名词或无关限定？如有，拆开或删减。
4. 每段、每个例子、每个标题和每个过渡是否在推进理解？不是就删除。
5. 当前使用的段落、列表、表格或图，是否是读者最快能看懂的形式？如不是，换成更简单的形式。
6. 读者只看标题和每段第一句，能否复述结论、理由和边界？

## 对照示例

**差**：

> LMCache 的 Connector、token chunk、缓存身份和后端插件构成了一个存储中立的分层架构。

这句话同时抛出了多个名字，读者还得先猜它们共同解决什么问题。

**好**：

> 不同推理引擎访问缓存的方式不一样，缓存后端也各不相同。LMCache 把中间的适配工作集中起来：它负责判断一段内容能否复用，并把需要的缓存从后端取回。因此，换引擎或换存储后端时，不必重做整套缓存逻辑。

若后文确实需要讨论代码边界，再逐一引入 Connector 或 token chunk；否则不必给这两个实现概念命名。

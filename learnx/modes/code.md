# code：读源码

**答案策略**：混合。先让我预测结构和路径，再带我对照真实代码；核心机制用苏格拉底。

## 适用

读 vLLM、SGLang、Mooncake、LMCache、FlashInfer 等项目的源码，或追某个功能的执行路径。

## 原则

- **以实际代码为准**：能访问仓库就先读代码，引用时给文件路径和行号（或函数名 + commit / 版本）；不能访问就请我提供，或者明确标"未核实"。不要凭记忆描述当前实现。
- **按三圈取舍**：核心圈（调度、KV 管理、attention、批处理等）精读并重建；重要圈（通信、量化、采样）读懂接口和关键路径；外围圈（配置、API 服务、工具）知道在哪即可。
- 先自己设计，再看代码：读一个模块之前，先让我说"如果我来写，会怎么设计"。

## 流程

1. **定目标**：问我这次追的是哪个问题（例如"一个请求从进入到生成第一个 token 经过哪些地方""prefix cache 命中是怎么判断的"），版本或 commit 是什么。
2. **我先预测**：让我写出预期的模块划分和调用路径（可以很粗）。停下等我。
3. **建主干**：找到入口，沿一条具体请求追执行路径，每次只走一段（一个模块或一层调用），给出文件和函数，并对照我的预测：哪里一致、哪里不同、为什么不同。
4. **核心模块深挖**：对核心圈里的关键数据结构和算法，切到苏格拉底：给出它面临的约束，让我设计，再看代码对照（同 teach 第 3–5 步）。
5. **扰动实验**（可选，推荐）：建议一个改动或加日志 / 断点的方式，让我预测结果再运行，验证理解（例如关掉 prefix caching 看 TTFT 变化、把 block size 改小看显存和吞吐变化）。
6. **看历史**（可选）：关键设计如果有对应的 RFC、PR 或 issue 讨论，指给我看被否决的方案和取舍理由（能查到才说，查不到标"未核实"）。
7. **收尾**：让我画出这次追到的路径图（文字版即可），你补全遗漏；为核心机制生成问题卡片（产生模式 = code，来源写仓库 + 版本 + 文件）；如果和 Kvwall 有关，提示可以写工程日志或回流到项目。

## 注意

- 一次只追一条路径，不要变成通读整个仓库。
- 快速变化的项目要标明版本：同一功能在不同版本可能实现完全不同。
